# Quarterly generator toolchain recommendation

Decision proposal for #0010, 2026-10-30. This evaluates the offline generator; it does not authorize a rewrite or a dependency upgrade.

**RECOMMENDED: Python with Polars, a small ZIP import layer, and private quarter-partitioned Parquet summaries.** Keep TypeScript for the static website. Separate the generator's core dependencies from the optional Iceberg and XLSX tools.

The strongest reason is the combination of suitable native execution, direct reuse of the canonical normalization and tested importer, and a simple path to incremental quarterly processing. This is a maintainability judgment, not a measured claim that Polars beats DuckDB. Python plus DuckDB is a credible close alternative. TypeScript with either native DuckDB or `nodejs-polars` is technically sound if using one language matters more to Terry than preserving the current analysis code.

## What the generator needs to produce

The primary product is a vendor-grouped matrix comparing models by relative model quarter. The exact starting point remains an owner decision: first observed model quarter is a proposal, while starting at the legacy minimum-population threshold has not been agreed either. Each cell combines cumulative AFR, observed population, new observations, failures and inferred decommissions. Calendar-quarter exploration remains useful as a secondary view. This is a model's observed history, not a drive-age cohort or a measurement of physical disk age.

The workload is a deliberate local run about once per quarter. Minutes of processing are acceptable; correct history, repeatability, modest operational effort and a small static result matter more than request latency. The generator can use ZIP CSVs or Iceberg as source adapters without making either format part of the browser contract.

Repository evidence:

- The existing ZIP import projects six relevant columns and processes daily members individually. `drive_model_names.py` is already shared by the exporter and original workbook script.
- The recorded 2026 Q2 import contains 91 daily CSVs and 31,968,003 observations. Its projected Parquet cache is about 222 MB; the selected public JSON is about 12 KB for 38 normalized models and 333,560 observed drive identities. These are existing validation results, not new benchmark measurements. See [validation evidence](web-validation.md).
- The exporter runs a fixed number of source queries and retains drive-quarter summaries, rather than daily Python objects. However, `summarize_source()` collects those summaries and subsequent work is eager. Memory grows with history and group cardinality; the current exporter is not a fixed-memory history processor. See [the current contract](web-data.md).
- Only 2026 Q2 history is loaded locally. No language choice makes that sufficient for the flagship historical comparison. Earlier history must eventually be obtained and validated within an explicitly chosen coverage window.

## Comparison

The assessments below distinguish engine capability from the cost of adopting it here. They do not rank raw execution speed: no equivalent multi-engine benchmark was run.

| Candidate | Where the large computation runs | Strengths for this job | Costs and limits here |
| --- | --- | --- | --- |
| Python + Polars | Rust columnar parser, expression and grouping engine | Existing importer, normalization and tests; concise transformations; native CSV/Parquet; easy Python orchestration | Dynamic frame schemas still need checks. Existing eager summaries can grow large. Streaming and spill support depend on the pinned version and exact query. |
| Python + DuckDB SQL | Embedded native analytical SQL engine | Strong SQL aggregation, joins, windows, disk spilling and persistent staging; Python keeps ZIP handling and canonical normalization | Rewrite and parity-test the aggregation layer; manage SQL result types and query schemas. A database is optional, but persistent state adds migration/recovery work. |
| TypeScript/Node + native DuckDB | The same DuckDB engine, called through `@duckdb/node-api` | One host language across generator and web; good CLI/domain types; SQL handles the large data without JS row loops | Port or isolate Python normalization; choose a ZIP library and preserve CRC/path/date checks; explicit integer/JSON conversion; native package/platform pinning. SQL columns remain runtime data. |
| TypeScript/Node + native Polars | Rust Polars engine through `nodejs-polars` | One host language; typed dataframe/expression API; lazy CSV/Parquet and native grouping; familiar transformation model when porting Python Polars | Validate the Node release's actual API and engine features rather than assuming Python parity; port normalization and ZIP safeguards; check integer conversion and native platform packages. |
| Rust + Polars | The same Rust Polars engine, called directly | Strong host-language types; native ZIP/Parquet integration; a compiled CLI can be convenient to distribute | Rewrite cost and additional build/feature management. Rust's type system does not prove a lazy dataframe query's runtime schema or metric semantics. There is no demonstrated need for custom kernels. |

Polars documents a Rust core and native parallel/vectorized execution across its language bindings. Lazy queries support projection and predicate pushdown, which are useful when scanning narrow Parquet caches. Calling that engine from Python does not turn each drive-day into a Python calculation. Calling it directly from Rust does not automatically accelerate an equivalent query. [Polars overview](https://docs.pola.rs/), [lazy optimizations](https://docs.pola.rs/user-guide/lazy/optimizations/).

Likewise, a TypeScript implementation using native DuckDB or `nodejs-polars` can perform parsing and aggregation outside JavaScript. Rejecting it because JavaScript row loops would be slow would compare the wrong designs. Select only small aggregate results into the host language; avoid collecting all daily observations into Python lists, JavaScript objects or a browser.

For raw ZIP ingestion, all candidates still pay decompression and CSV parsing costs. Column projection reduces retained data and downstream work, but does not allow an ordinary compressed CSV to skip reading all unwanted bytes. Preserve the existing daily staging boundary. Do not assume that changing the query engine means it can safely read ZIP members directly; use a verified streaming adapter or private temporary daily file when the engine requires a path.

### Memory and current support

DuckDB documents disk spilling for grouping, joins, sorting and windows, including when intermediates exceed memory. It also documents remaining out-of-memory cases involving multiple blocking operators and some complex aggregate states. Configure a private spill directory and memory budget; stage queries when needed. Fetching a huge final result into Python or Node still consumes host memory. [DuckDB workload tuning](https://duckdb.org/docs/2.0/guides/performance/how_to_tune_workloads.html).

Polars' current 2.1 announcement, dated October 27, 2026, adds out-of-core high-cardinality grouping and streaming windows after 2.0 introduced default spilling. That materially weakens an argument that DuckDB is the only credible larger-than-memory choice. It does **not** describe the repository's tested 1.41.2 environment: `requirements.txt` also still lists 1.39.0. Do not promise current spill behavior without an explicit upgrade, query-plan inspection and constrained-memory validation. [Polars 2.1 announcement](https://pola.rs/posts/polars-2-1-changelog/).

Polars also documents a default approximately 4.3-billion-row dataframe index limit, with a 64-bit-index option. Processing and persisting one quarter at a time avoids requiring a single full-history daily dataframe; it does not eliminate all intermediate-memory limits. [Polars installation and index options](https://docs.pola.rs/user-guide/installation/).

The official DuckDB documentation currently identifies the Node Neo stable client as 2.0.0, supports Windows AMD64 and ARM64, and lists some unfinished APIs, including Arrow APIs and profiling information. The required SQL/Parquet aggregate path does not depend on those unfinished APIs. Its `BIGINT` results become JavaScript `bigint` by default; JSON helpers can instead serialize them as strings. Explicitly convert validated safe counts to the site's numeric contract. [DuckDB Node Neo API](https://duckdb.org/docs/2.0/clients/node_neo/overview.html).

The official `nodejs-polars` package manifest identifies version 0.26.1, Node >=20 and a Windows x64 native target. Its Cargo manifest selects Polars 0.55.2 with lazy and Parquet features. This is a separate binding/version line; Python Polars 2.1 release claims cannot establish its streaming or spill behavior. Inspect the pinned Node API and physical plan, then validate resource use for the actual grouping/query. [Node package manifest](https://raw.githubusercontent.com/pola-rs/nodejs-polars/main/package.json), [native dependency manifest](https://raw.githubusercontent.com/pola-rs/nodejs-polars/main/Cargo.toml).

The Node API exposes lazy Parquet scanning, grouping, joins and collection, making it a credible native dataframe alternative to SQL. Its published TypeScript schema generics help with supported operations, but external input and transformed schemas still need runtime checks. Its CSV stream helper currently buffers the entire stream before parsing: preserve a one-day boundary or use a private staged file. For integer columns, verify the pinned binding's number/`bigint` conversion and JSON behavior; range-check any conversion to the site's numeric counts. [Node lazy API](https://pola-rs.github.io/nodejs-polars/interfaces/pl.LazyDataFrame.html), [scan and stream implementation](https://raw.githubusercontent.com/pola-rs/nodejs-polars/main/polars/io.ts).

## Dependencies and packaging

For the proposed Python generator:

- **Core runtime:** one supported Python minor version and Polars. Use standard-library ZIP, date, hashing, filesystem and JSON facilities. Preserve `drives_of_interest_regexes.json` and import the canonical normalizer rather than copying it.
- **Reproducibility:** a checked-in `uv.lock` and documented locked commands. Unify the currently inconsistent dependency declarations before treating them as reproducible. Start from the environment already verified here; evaluate a newer Polars version separately. uv supports locked execution that refuses an outdated lock. [uv locking and syncing](https://docs.astral.sh/uv/concepts/projects/sync/).
- **Optional adapters:** isolate the existing Iceberg/S3 dependencies and `xlsxwriter` from ZIP-to-static-JSON use. Do not require PyArrow, pandas, a server database, Spark or cloud infrastructure for the core path merely because the older environment contains related packages.
- **Verification tools:** retain the existing small Python tests and frontend contract checks. Add a Python type checker if useful for domain structures; it complements runtime dataframe and JSON validation. A new testing framework is not required for this decision.

If choosing DuckDB instead, use the `duckdb` Python package or Node's `@duckdb/node-api`, a ZIP reader appropriate to that host language, and the same private Parquet and JSON contracts. Avoid keeping two production aggregation engines solely to hedge the decision. A small independent SQL reconciliation query can still be useful evidence without becoming a second maintained application.

For TypeScript + Polars, the core engine dependency is `nodejs-polars`, with TypeScript/Node tooling and a verified ZIP reader. Pin its package and native artifacts in the npm lockfile; test the selected Windows x64 installation instead of relying on declared targets alone. Port canonical normalization only with shared parity fixtures, or retain a narrow Python normalization boundary while acknowledging that this keeps two runtimes. Reuse the personal regex file and validate regex semantics. Domain/JSON types can be shared with the frontend, but the generator remains an offline Node program: the native engine is not shipped to the browser. This option trades a bounded rewrite and binding-specific validation for a single host language and a dataframe API close to the existing design.

## Process a new quarter without rescanning every old ZIP

The important architectural change is persisted sufficient summaries, regardless of language.

1. **Import once:** verify the new ZIP and daily dates, record its checksum/schema/coverage, and retain projected private Parquet. Reuse the existing checks for paths, CRC, required columns and duplicate observations.
2. **Summarize that quarter:** persist one record per normalized model/serial/quarter with observed drive-days, the SUM of daily failure flags for AFR, first/last observation and any required endpoint/datacenter fields. Keep separate failure-identity and failure-date state sufficient for the chosen decommission rules; a boolean ever-failed value must not replace the failure-flag sum. Also retain model/capacity frequency counts and date coverage. Per-drive keys remain private.
3. **Build history from summaries:** obtain first model quarter, per-drive first/last history and model-quarter totals. Compute cumulative AFR from cumulative failure and drive-day sums, never by averaging quarterly percentages. Apply vendor grouping and model-age coordinates to the compact model-quarter result.
4. **Publish aggregates:** emit a versioned matrix/history contract with coverage and metric definitions. Keep a deterministic rebuild path from immutable inputs and summaries.

Initially, regenerating the compact summaries/history is simpler to audit than maintaining mutable global lifecycle counters. This still avoids decompressing every old ZIP and scanning every old daily row each quarter. If serial-quarter summaries later become too large, scan them lazily or use disk-backed staging instead of eagerly collecting all of them.

Cache identity must include source checksum, summary schema, normalization version and metric version. If a cache is filtered, include the selection-file content hash too. Prefer retaining an unfiltered projected cache so changing personal interests does not require another ZIP download. Replacing a corrected quarter must invalidate its summary and all dependent cumulative/lifecycle outputs; adding older history can move model-age anchors and change first-observed counts. Rerunning the same quarter must replace or reuse validated state, never append it twice.

## Correctness decisions that outrank the language choice

- **Model-age axis:** the owner must choose whether quarter 1 means first observed quarter or first quarter meeting an agreed population threshold. First observed quarter is proposed here; neither that choice nor the legacy threshold anchor is approved. Keep actual calendar-quarter offsets and gaps under either definition. Decide separately whether the threshold only controls display and whether cumulative AFR retains earlier observed exposure; do not change either silently. Label anchors limited by dataset coverage.
- **Common population:** use the same personal regex selection and canonical normalized identities for every displayed measure. Keep model plus serial as the private identity. A language or SQL port needs alias/whitespace/regex parity tests, not merely similar-looking model names.
- **Decommission inference:** the current `lastObservedDrives` explicitly includes failures and is provisional. It cannot simply be renamed decommissioned while failures are displayed alongside it as a separate category. Specify whether inferred decommissions exclude failed identities, the required observation horizon/grace period, and treatment of disappear/reappear cases. An absence is not confirmed physical retirement.
- **As-of versus revised history:** state whether a historical cell shows only evidence available through that quarter or a retrospective inference using later data. Keep those semantics explicit; later observations must not silently change a historically as-of bundle. Preserve provisional boundary cases and expose the inference cutoff.
- **Population semantics:** unique drives observed anywhere in a quarter differ from quarter-end fleet. Do not claim a stock-flow identity between quarter-to-quarter population deltas, new observations, failures and decommissions unless the chosen definitions actually satisfy it. Include observed drive-days and failure counts so a striking AFR has context.
- **JSON publication:** enforce finite numeric values, integer/nonnegative counts, stable model IDs, deterministic sorting and no serials. Validate the entire staged generation against the browser contract before replacing its manifest. For revised history, use immutable generation paths or content-hashed bundle names and switch the manifest last; overwriting stable filenames is not an atomic multi-file release.

The new matrix needs a reviewed contract extension or version change. The current per-quarter bundle contains only models present in that quarter; it is not yet the complete lifetime matrix, including models that disappeared before the latest quarter. The contract should retain historically observed models and explicitly represent unavailable cells.

## What would change this recommendation

Python + DuckDB becomes more attractive if SQL is Terry's preferred way to maintain these transformations, or if representative multi-quarter processing shows Polars failing the available memory budget after staging and an appropriate supported-version evaluation. Both TypeScript candidates become more attractive if avoiding a second host language is a strong maintenance preference. Choose between native DuckDB and `nodejs-polars` based on SQL versus dataframe maintenance preference, verified API coverage and a representative resource check. The Node Polars route could become the preferred choice if its pinned binding covers the required queries and the normalization/import parity work is acceptable; Python has no inherent engine-speed advantage. Python remains the proposal here because the existing normalization/import path is already validated and binding migration has no demonstrated operational payoff yet. Rust becomes attractive if distributing a self-contained CLI or writing custom native processing is a concrete requirement. None is established by the quarterly cadence alone.

Before implementing the flagship generator, agree the history window, model-age anchor, population threshold and decommission inference. Then validate a small multi-quarter fixture covering gaps, aliases, returns, failures and cutoff changes; reconcile the already downloaded real quarter; and measure elapsed time, peak memory and temporary disk on a representative historical slice. Do not extrapolate a guaranteed full-history resource requirement from the 222 MB compressed quarter cache.

This evaluation inspected repository code and documentation and checked current official engine/client documentation. It did not install alternative engines, download history, run cloud jobs, upgrade dependencies or conduct a performance benchmark. The operational recommendation remains conditional on normal acceptance tests and resource measurement; the existing single-quarter validation is evidence of current behavior, not proof that the proposed matrix is already implemented.
